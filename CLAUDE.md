## Project Overview

Smart Funnel is a Flutter app for the **funnel owner**. The owner connects their phone to a Raspberry Pi Pico W mounted on their beer funnel via BLE. After each chug, the Pico sends the measured chugging time to the app. The owner then enters who just chugged, what they drank, and the quantity. The result is saved to Firestore under that funnel's leaderboard.

The app's default state is the leaderboard for the connected funnel, filterable by liquid type and quantity. There are no user accounts — the funnel is the identity.

This is a hobby/party project. Keep it simple.

## Stack

- **Flutter** (Dart) — iOS + Android from a single codebase.
- **flutter_blue_plus** — BLE. Receives the chugging time from the Pico after each chug.
- **Firebase / Cloud Firestore** — persistence. Chug records are documents in a single `chugs` collection, no auth. Firestore's built-in offline persistence covers offline reads.
- **shared_preferences** — kept only so `legacy_import_service.dart` can read and migrate any pre-Firestore local leaderboard data still on a device; not used for anything else.
- **Riverpod** (`flutter_riverpod`) — lightweight state management. Use it where it earns its keep; don't over-provider.
- **go_router** — routing.

No SQLite, no Dio, no custom backend, no build flavors, no Firebase Auth.

Firebase project: `smart-trichter-67`. Android is fully configured (`google-services.json`, Gradle plugin wired). iOS is **not** configured — `lib/firebase_options.dart` has a stale `ios` entry left over from an earlier (different) Firebase project; ignore it / regenerate via `flutterfire configure` before ever building for iOS.

## BLE Protocol (contract with firmware)

The Pico W advertises a custom GATT service. Keep UUIDs in sync with the firmware repo.

- **Service UUID**: `0000FUN1-0000-1000-8000-00805F9B34FB` (placeholder — replace before first hardware test)
- **Chug Result characteristic** (notify): the Pico sends a single payload after chugging ends.
  - Format: 4-byte little-endian unsigned int = duration in milliseconds.
  - Example: `0xA3 0x0C 0x00 0x00` = 3235 ms.

App behavior:
1. Scan filtered by service UUID.
2. On connect, subscribe to notifications on the Chug Result characteristic.
3. On receiving a payload, decode the duration and open the log-chug form.
4. The BLE device address is the **funnel ID** — stored as `funnelId` on each chug document and used as the query filter.
5. On disconnect, show a reconnect prompt. No auto-reconnect logic.

## Chug Logging Flow

1. Pico sends chug duration → app receives it via BLE notification.
2. App immediately opens the log-chug form (modal bottom sheet or separate screen — bottom sheet preferred).
3. Owner fills in:
   - **Name** — free text, required.
   - **Liquid** — dropdown or chip selector (e.g., Beer, Wine, Prosecco, Other). Required.
   - **Quantity (ml)** — number input. Required. Suggested values: 250, 330, 500, 1000.
4. Owner taps "Save" → written to Firestore → form closes → leaderboard updates.
5. "Discard" dismisses without saving.

The same form (`LogChugSheet`) doubles as the **edit** form: pass an existing `ChugRecord` and it prefills, adds an editable "Duration (ms)" field (not shown when logging a new chug — that value always comes from the Pico), and calls `FirestoreService.updateChug` instead of `saveChug` on submit. `funnelId` and `loggedAt` are preserved from the original record, not editable.

## Firestore Data Model

Collection: `chugs`. One document per chug; the document ID is the record ID (no app-generated ID).

Each document:
```json
{
  "funnelId": "string",  // BLE device address of the funnel
  "name": "string",      // Who chugged
  "liquid": "string",    // e.g. "Beer"
  "quantityMl": 330,
  "durationMs": 3210,
  "loggedAt": Timestamp  // server-assigned on create (FieldValue.serverTimestamp())
}
```

All records in one flat collection, filtered by `funnelId` in queries.

Collection: `funnels`. One document per funnel ever connected to; document ID is the `funnelId` (BLE device address). Written (merged) on every successful BLE connect, from `connectedDeviceName` — this is how a funnel can later be found by name and its leaderboard browsed without an active BLE connection.
```json
{ "name": "string" }  // BLE-advertised name at last connect
```

**Security rules** (`firestore.rules`): open `read`; `create`/`update` require the fields above with correct types (same pattern for both `chugs` and `funnels`); `delete` is open. No Firebase Auth — consistent with the app having no user accounts. This means anyone with the app's Firebase config can edit or delete any funnel's entries; that's an intentional tradeoff for a hobby/party app, not an oversight. Don't add Auth to tighten this without discussing it first.

## FirestoreService

`FirestoreService` wraps `cloud_firestore` and exposes:
- `saveChug(ChugRecord)` — adds a document (server-timestamps `loggedAt`).
- `updateChug(ChugRecord)` — overwrites an existing document's editable fields, preserving its original `loggedAt`.
- `deleteChug(String id)` — removes a document.
- `saveAll(List<ChugRecord>, {preserveLoggedAt})` — batched writes; used by the legacy import to backfill original timestamps instead of "now".
- `watchLeaderboard({funnelId, liquid?, quantityMl?})` → `Stream<List<ChugRecord>>` — filtered + sorted ascending by `durationMs`.
- `watchAllLeaderboard({liquid?, quantityMl?})` → `Stream<List<ChugRecord>>` — same, no funnel filter.
- `saveFunnelName(String funnelId, String name)` — upserts a `funnels` document; called on every successful BLE connect.
- `watchKnownFunnels()` → `Stream<List<KnownFunnel>>` — all funnels ever connected to, sorted by name.

Both stream methods listen to a single unfiltered `chugs` collection snapshot and filter/sort client-side in Dart, rather than server-side `where`/`orderBy` queries — this avoids needing a Firestore composite index per filter combination, which isn't worth the complexity for this small collection. Keep it this way; don't "optimize" into server-side compound queries without a real scale reason.

The service is exposed via `firestoreServiceProvider` (plain `Provider`, synchronous construction).

## Legacy Local Data Import

`features/ble/legacy_import_service.dart` is a one-time bridge for devices that still have chugs saved under the old shared_preferences-based storage (`chug_records` key), from before the app moved to Firestore. The Connect screen shows an "Import N local chugs to Firestore" button only while such data exists; it asks for confirmation, batch-writes to Firestore preserving original timestamps, then clears the local key so the button disappears. Delete this feature (and the `shared_preferences` dependency) once no users have local-only data left to migrate.

## Leaderboard (Default and Only Screen)

- Shows all chugs for the **currently connected funnel** (filter by `funnelId`).
- Sorted by `durationMs` ascending (fastest at the top).
- App bar title shows the connected funnel's BLE advertised name (`connectedDeviceNameProvider`), falling back to its MAC address, then to "Smart Funnel" if nothing is connected.
- Filter controls at the top:
  - **Liquid** — "All" + the distinct liquid types in the dataset. Chip-style selector.
  - **Quantity** — "All" + distinct quantities. Chip-style selector.
- Each row: rank, name, duration (formatted as `ss.SSS`s), liquid, quantity, and when it was logged (`formatChugTimestamp`, e.g. "Today, 14:32"). A per-row overflow menu (⋮) offers **Edit** (opens `LogChugSheet` prefilled, see Chug Logging Flow) and **Delete** (confirmation dialog, then `FirestoreService.deleteChug`).
- If no funnel is connected, show all chugs across all funnels or a "Connect a funnel" prompt.
- Leaderboard updates reactively via `StreamProvider`.
- There's no separate history/log screen — the leaderboard (with its timestamp column and filters) is the single source of truth for past chugs. Don't re-add one; if a chronological (rather than fastest-first) view is wanted later, that's a sort-order toggle on this screen, not a new screen.

### Browsing a Disconnected Funnel

The Connect screen has a "Browse a funnel's leaderboard" entry (`/funnels`, `FunnelSearchScreen`) below the BLE scan/connect controls, for viewing a funnel's leaderboard without an active BLE connection. It's a search-by-name box over `watchKnownFunnels()`; picking a result sets `browsingFunnelProvider` and goes to `/leaderboard`. `leaderboardProvider` uses `connectedDeviceIdProvider` when set, else `browsingFunnelProvider`'s id — a live connection always wins. While browsing this way (no live connection, a funnel picked), the leaderboard app bar shows a "Change funnel" button that returns to `/funnels`; connecting for real clears `browsingFunnelProvider`.

## devcontainers Note

BLE is on the **host** Bluetooth stack, not inside the container. Flutter's BLE plugin (`flutter_blue_plus`) calls the host OS's BLE APIs at runtime — this only matters when running the app **on a real device**. The code compiles and the emulator runs normally from inside the container.

However:
- `flutter run` targeting a **physical device** via USB/ADB must be run from the host, not the container, unless USB passthrough is configured (via `usbipd` on Windows/WSL2 or `--device-cgroup-rules` on Linux).
- Emulator/simulator targets work from inside the container as normal.
- Hot reload and `flutter analyze` work inside the container regardless.
- Document the host-side run steps in the README so the workflow is clear.

## Testing

- Unit test Firestore serialization (ChugRecord `toFirestore`/`fromFirestore` round-trip) using `fake_cloud_firestore`.

- Unit test `legacy_import_service.dart` using `SharedPreferences.setMockInitialValues({})` + `FakeFirebaseFirestore()`.

- Skip widget tests for simple screens.
- BLE integration: manual, on real hardware.

## What NOT to do

- Don't add SQLite or another local DB — Firestore's offline persistence covers offline reads.
- Don't add Firebase Auth or user accounts — the leaderboard's open Firestore rules are a deliberate no-auth tradeoff for a hobby/party app.
- Don't add build flavors or env files.
- Don't add analytics, crash reporting, or remote config.
- Don't add a `domain/` layer, repository interfaces, or use-cases.
- Don't auto-reconnect BLE — show a prompt instead.
- Don't measure chug duration on the phone — trust the Pico's value.
- Don't rewrite `FirestoreService`'s client-side filtering into server-side compound queries without a real scale reason (see above — it'd require composite indexes).
